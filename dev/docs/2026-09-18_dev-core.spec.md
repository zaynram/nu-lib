# `dev`: ticket files, the local surface of Todoist tickets

Module `_internal/dev`. Sibling modules named below (`util`, `repo`, `todo`, `elevate`, `completion`)
live at `_internal/<name>/mod.nu`. `td` is the Todoist CLI, `claude` the Claude Code CLI. "The remote
host" is the issue tracker of the repository's git remote; the design uses only issues, milestones,
issue state and Markdown bodies, so no single provider is assumed. GitHub, through `gh`, is the one
host wired today.

Written 2026-09-18 as a clean rewrite of the 2026-09-15 draft and its amendments; the decisions keep
their numbers. D6 to D9 concern `dev sync` and are recorded in `dev/docs/2026-09-18_dev-sync.bindings.md`,
which also collects every commitment this spec makes for sync and states, in its Scope section, what
`dev sync` is and is not responsible for. That document is mandatory reading before writing or
implementing anything that touches `dev sync`, `edit --add-task`, `edit --complete` or the `--md`
body; this spec does not repeat it. The sync spec itself (`dev/docs/<date>_dev-sync.spec.md`, Phase 4
of `dev/docs/_design/05-plan.md`) is not written yet.

## Purpose

Replace the nupm `issue` and `tasks` modules (`~/.local/share/nupm/modules/{issue,tasks}`) and their
v3 `issue` schema (`version = "3.0.0"` files under `docs/issues/` of the registered repositories) with a
v4 `ticket` schema and six local commands: `dev` (load), `list`, `query`, `edit`, `new`, `migrate`. One
`<repo>/docs/tickets/<slug>.toml` per ticket is the only local store; there is no cache, index or
mirror. The `ticket` schema descends from `issue` in structure only; the v4 label marks the succession.

## Ownership

Three surfaces hold a ticket. Each datum has exactly one owner; `dev sync` moves it away from its owner,
and only the write paths named here move anything toward an owner:

- **Todoist** owns the ticket's existence, its kind label (`%deliverable`/`%actionable`), its task rows
  (the direct subtasks of the ticket task) and reopening. A ticket is one Todoist task whose `content`
  is the slug, in the project named after the repository (or a project alias on the repository's row in
  the `repo` registry `$env.repo.path`; that column lands with Phase 3b of the plan). Three paths write
  a row back to Todoist: `dev edit --add-task` (a row added locally), `dev edit --complete` (a row
  completed locally), and `dev sync` applying a box ticked or unticked on the remote issue's `## Tasks`
  checklist (a completion or un-completion made on the host). Nothing else changes a row from outside
  Todoist: content, description, labels, order and existence change in Todoist only.
- **The ticket file** owns the body (`outcome requirements constraints output scope landscape bindings
  extends`), `status` and `target`. `[[tasks]]` and `[ticket.reference]` are mirrors that `dev sync`
  writes; `[[tasks]]` also records the row state at the last sync, which is how a box toggled on the
  host is told apart from one toggled in Todoist (bindings document, D8).
- **The remote host** holds projections only: the issue (title = slug, body = `dev <slug> --md`,
  milestone = `target`) and the milestone (title = `target`). Two things flow back from the host:
  closing the issue is accepted as closure (D6), and a box ticked or unticked in the `## Tasks`
  checklist is applied to the matching subtask in Todoist (D8). Checklist lines added, removed or
  reworded on the host are not read; the body is rewritten from Todoist on every sync, so they do not
  survive it.

Ticket, Todoist task, remote issue, ticket file and git branch share one name, the slug (D13).

## Decisions

Recorded under the `/ponytail` rule (the least design that works). D1 to D5 and D10 to D15 were
authored by the user on 2026-09-15 against the 14 shipped v3 files
(`~/code/{nu-fluency,nushell-mcp,ramda-doc}/docs/issues/*.issue.toml`); D1, D2, D12 and D13 were
re-decided on 2026-09-17/18 in the sync design thread (`dev/docs/_design/07-lifecycle.d2`).
`$td_task` below is the ticket's Todoist task, `$td_subtask` one of its direct subtasks.

- **D1: one tier of rows, mirrored from Todoist.** The v3 `[tasks]` table (digit-keyed objects with
  nested `subtasks`) becomes `[[tasks]]`, one row per direct subtask of `$td_task`, in Todoist order:

  ```toml
  [[tasks]]
    content = 'string' # $td_subtask.content
    description = 'string' # $td_subtask.description, optional
    labels = ['-human'] # $td_subtask.labels: at most one attribution label, one of -human, -agent, -mixed
    completed = false # $td_subtask.completed
  ```

  The ticket itself has no row. Its kind label is set once by `dev sync` when it creates `$td_task`
  (`%deliverable` when `[[ticket.output]]` is non-empty, else `%actionable`) and is Todoist's afterwards;
  the file stores nothing for it. Every label `dev sync` or `dev edit` attaches must already be one of
  the user's Todoist labels (`todo labels`); none is ever created, because `td task add --labels <x>`
  accepts any string and attaches it as a shared label without creating one (probe 2026-09-19).
  Rows carry no `%` label and no deeper nesting. `dev sync` applies
  any box toggled on the host to Todoist (Ownership) and then rewrites `[[tasks]]` wholesale;
  `edit --add-task` and `edit --complete` write through to Todoist first.
- **D2: no task migration; the v3 task table is dropped.** `dev migrate` neither creates Todoist tasks
  (probe 2026-09-19: two of the eight unfinished v3 files, `pathext-omission` and `run-raw-routing`,
  have no Todoist task; `windows-portability-batch` is completed in Todoist while its v3 file says
  `open`, which the first `dev sync` resolves by D6) nor carries the v3 `[tasks]`
  table anywhere: its history stays in git under `docs/issues/`, and the eight unfinished files are few
  enough to re-enter by hand. A `ticket.notes` checklist was considered and rejected on 2026-09-18 as a
  field for one migration. Two files carry v3 shapes with no v4 home and are refused until hand-edited:
  `nu-over-bash-hooks` and `polyglot-reference-autodoc-tooling` (paths under Migration mapping). No
  generic mapper.
- **D3: duplicate slugs are errors.** A slug present in more than one registered repository errors on
  every command that takes a slug; `--repo <name>` is the only disambiguator.
- **D4: dates are written quoted.** `date` serialises as `"YYYY-MM-DD"` on every write (`to toml`
  would otherwise emit `2026-09-14T00:00:00.0+00:00`); any value `into datetime` accepts is read.
- **D5: `dev new --prompt` has a tight I/O contract.** User-authored signature, kept verbatim except
  the `--numchar` bullet, replaced on 2026-09-19 by the user's ruling below:

  ```nu
  def "main new" [
    # ...
    --prompt (-p): string
    # Enables generation when passed; user prompt to submit for the generation
    --recover (-r): path
    # Saved reply to validate and write instead of generating; with `--prompt`, resume the reply's Claude
    # session with the new prompt (`claude -p --resume <id>`, the id is in the saved reply's file name)
    --files (-f): list<path> = [$EXAMPLE]
    # Files to include in the context for the generation; `const EXAMPLE: path = path self ./docs/example.toml` (the example file below)
    --edit (-e)
    # Open the written file with the `util editor` (custom `editor` definition from `util` sibling module)
    --interactive (-i)
    # Calls `input` per header with the following parameters:
    #  - (argument) $"(ansi bb)($head)(ansi rst) (ansi bd)($desc)(ansi w):(ansi rst) "
    #    - ANSI styling for separation of prompt text from user's input text
    #    - $head = The header name
    #    - $desc = Short description/criteria of what the input text should contain
    # - (option) `--history-file=<tempfile>`
    #    - History file for storing input from partial completion (include path in any errors/interrupts during wizard)
    # - (option) `--reedline`
    #    - Allows for multiline input; can be omitted since it is implied when using `--history-file` but listed here for transparency
    # - (option) `--suppress-output`
    #    - Disable printing of keystroke values
    # - (validation) a value failing its field's check is re-prompted for that field with the reason,
    #   so the wizard is never rerun for one bad entry; no `--numchar` (no v4 field carries a length
    #   limit, and the four prompted fields named under Behaviour are free text, so no check fails today)
    # - (option) `--default=<default>`
    #    - Only passed for fields that have a configured default value
    #    - Description should include the existence and showcase of the default value for saliency
    --continue (-c): path
    # Path to an `input` history file from an incomplete `--interactive` run; implies `--interactive`
  ]: [
    nothing -> error # If the raw reply TOML fails validation, include the relevant path to a tempfile (interactive history or saved generation reply) in the error
    nothing -> path # If the raw reply TOML passes validation, save it to the appropriate location and return the path
    nothing -> nothing # If `--interactive` and `--edit` are passed and validation succeeds, open the path in the editor and return nothing
  ] {
    # ...
  }
  ```

  Verified 2026-09-19 through a pseudo-terminal: `input --numchar N` returns the moment the Nth
  character is typed and cannot wait for Enter, so it cannot serve as a length cap (ruling: validate
  after `input` returns and re-prompt); `--default` applies on a bare Enter; `--reedline
  --history-file --suppress-output` needs a real terminal, echoes the typed text through the line
  editor, and appends each answer to the history file; under `--reedline` Enter submits and Alt+Enter
  or Shift+Enter inserts a line break, stored in the history file as `<\n>`. The other collectors in
  0.115.2-nightly.24 (`input list`, `input listen`, `keybindings default|list|listen`) are not used:
  no prompted field is an enumeration and none needs raw key events.

- **D10: landscape rows differ by `scope`.** A v3 `issue.vision.landscape.internal[]` row becomes a
  `[[ticket.landscape]]` row with `scope = "internal"`; a v3 `issue.vision.landscape.external[]`
  string becomes a row with `scope = "external"` and `synopsis = <string>`. Every shipped row would
  have carried a `group` equal to its `scope`, so there is no `group`.
- **D11: flat bindings differ by `kind`.** A v3 `[[issue.bindings.xabort]]` becomes
  `[[ticket.bindings]]` with `kind = "xabort"`, `item = action`, `type = trigger.mode` and the optional
  `conditions = trigger.conditions`; `[[issue.bindings.xvalue]]` follows with `kind = "xvalue"`.
- **D12: one sync-owned description line.** The first line of `$td_task`'s description is a Markdown
  link to the remote issue in the form the live tasks already use,
  `[<slug> · Issue #<index> · <owner>/<repo>](<url>)` from `ticket.reference.remote`. `dev sync` owns
  that one line and never a hand-written one: when the first line already is such a link it is replaced
  (a stale link gets corrected), otherwise the link is prepended above whatever is there; every later
  line is left alone; a ticket without `reference.remote` gets no description write. Version-target
  tasks follow the same rule with their arrow line (bindings document). Row descriptions are free text,
  mirrored as-is.
- **D13: slugs are the universal name.** A v3 `extends` entry required a path
  (`docs/issues/<slug>.issue.toml`); v4 stores bare slugs, because a slug is the one name shared by the
  Todoist task (`content`), the remote issue (title), the git branch and the file stem. A slug matches
  `^[a-z0-9]+([+-][a-z0-9]+)*$`: kebab-case, `+` joining items that ship together (`+` is accepted by
  git branch names and as a Nushell bare word, verified 2026-09-18), no dots, so a slug can never be
  read as a version: `ticket.target`, milestone titles and `<repo>@<target>` Todoist tasks are the
  version-shaped names. Slugs name the work, not a version; the one dotted live task,
  `v0.4.0-close-out` (its v3 file already says `v0-4-0-close-out`), becomes `pre-version-ship-review`.
  Identity is repository + slug (D3); once linked, `dev sync` matches by `reference.todoist.id`, never
  by content.
- **D14: `--set` merges with overwrite.** `dev edit --set` merges into `ticket` with
  `merge deep --strategy=overwrite`: nested records merge, lists and scalars are replaced, so re-running
  the same `--set` is idempotent and `--set {constraints: []}` clears a list. `--add-task` is the append
  surface for the one list that grows.
- **D15: `migrate` moves the file.** A v3 file is read from `docs/issues/<slug>.issue.toml`, written as
  `docs/tickets/<slug>.toml` and the source removed; the result row reports both paths.

## Schema

`version = "4.0.0"`, TOML 1.0 valid, depth at most 3 (`[ticket.reference.remote]` is the deepest
header), one shape per key. `dev edit`, `dev new` and `dev migrate` build the record in this key order
before `to toml`, so every write is canonical: `version`, then `ticket` keys `name slug date status
target outcome requirements constraints extends output scope landscape bindings reference`, then `tasks`;
inside every array row and nested record the keys follow the column order of the table below (the v3
files order row keys differently, `purpose, path` and `type, item` among them, so `migrate` reorders).
`to toml` places scalar keys before sub-tables regardless of record order (verified 2026-09-18).

| key                         | type                                                                                                             | required | notes |
|-----------------------------|------------------------------------------------------------------------------------------------------------------|----------|-------|
| `version`                   | string                                                                                                           | yes      | `"4.0.0"` |
| `ticket.name`               | string                                                                                                           | no       | display name |
| `ticket.slug`               | string                                                                                                           | yes      | equals the file stem; charset in D13 |
| `ticket.date`               | string                                                                                                           | yes      | written `"YYYY-MM-DD"`, read as datetime (D4) |
| `ticket.status`             | string                                                                                                           | yes      | one of `draft`, `open`, `done`, `aborted`; `done`/`aborted` are the two close reasons of the remote issue |
| `ticket.target`             | string                                                                                                           | no       | release target, e.g. `"v0.4.0"` (live names carry the `v`; a target need not be a version); names the Todoist task `<repo>@<target>` and the remote milestone `<target>`; the file owns membership, `dev sync` projects it |
| `ticket.outcome`            | string                                                                                                           | yes      | may be empty |
| `ticket.requirements`       | list<string>                                                                                                     | yes      | may be empty |
| `ticket.constraints`        | list<string>                                                                                                     | yes      | may be empty |
| `ticket.extends`            | list<string>                                                                                                     | no       | slugs (D13) |
| `[[ticket.output]]`         | `path` string, `purpose` string, `alias` string                                                                  | no       | `alias` optional |
| `[[ticket.scope.excluded]]` | `item` string, `deferred` string or bool                                                                         | no       | `deferred` optional |
| `[[ticket.landscape]]`      | `scope` in `internal`/`external`, `synopsis` string, `reference` string, `type` string, `incompatibility` string | no       | `reference`, `type`, `incompatibility` optional (D10) |
| `[[ticket.bindings]]`       | `kind` string, `item` string, `type` string, `conditions` list<string>                                           | no       | `conditions` optional (D11) |
| `[ticket.reference]`        | `todoist = {id string, url string}`, `remote = {index int, url string, branch string}`                           | no       | written by `dev sync`, never hand-edited |
| `[[tasks]]`                 | `content` string, `description` string, `labels` list<string>, `completed` bool                                  | no       | mirror of `$td_task`'s direct subtasks, written by `dev sync` (D1); `labels` holds at most the attribution label, no `%` label |

Absent optional keys read as an empty list (arrays of tables) or null (`target`, `extends`,
`reference`, row-level optionals). Null values are compacted at every level before writing, so a file
never contains `"<Nothing>"` (what `to toml` emits for null).

Example: `docs/tickets/hooks-placement.toml` as `dev migrate` writes it (`[[tasks]]` rows appear once
`dev sync` runs). The same document ships as `dev/docs/example.toml`, the file `dev new --prompt` sends
to the model. It round-trips byte-identically through `open | to toml` and parses under `tomllib`
(verified 2026-09-18).

```toml
version = "4.0.0"

[ticket]
name = "Hooks Placement Decision"
slug = "hooks-placement"
date = "2026-08-21"
status = "aborted"
outcome = "singular"
requirements = ["A definite stance with rationale, recorded where future contributors will find it."]
constraints = [
    "Gates nu-over-bash-hooks; no hook implementation before this freezes.",
    "Decision class is author-owned (manual).",
]

[[ticket.output]]
path = "docs/decisions/"
purpose = "Recorded decision: plugin-level hooks.json versus skill-scoped frontmatter."

[[ticket.scope.excluded]]
item = "Hook implementation"
deferred = "nu-over-bash-hooks"

[[ticket.landscape]]
scope = "internal"
synopsis = "No hooks shipped yet; placement undecided."
type = "greenfield"

[[ticket.bindings]]
kind = "xvalue"
item = "Freezing placement before implementation prevents rework across every future hook the plugin ships."
type = "sequencing-integrity"

[ticket.reference.remote]
index = 5
url = "https://github.com/zaynram/nu-fluency/issues/5"
branch = "hooks-placement"
```

## Contract

Completers prefixed `_` are private to `dev/mod.nu`, each returned through `into completions` from
`_internal/completion` (`completion/mod.nu:41`): `_slugs` lists the tickets found by discovery,
`_v3-slugs` the `docs/issues/*.issue.toml` files, `_repos` the names in `$env.repo.path`, `_statuses`
the four statuses, `_properties` the cell paths of the loaded record.

```nu
# Load and validate a ticket; `--md` renders the remote issue body instead.
export def main [
  slug: string@_slugs
  --repo (-r): string@_repos # Repository to look in when the slug exists in more than one
  --md # Render the ticket as the remote issue body (Markdown) instead of returning the record
]: nothing -> oneof<record, string>
# dev hooks-placement | get ticket.status   # aborted

# Tickets across the registered repositories.
export def list [
  --status (-s): string@_statuses
  --repo (-r): string@_repos
]: nothing -> table<slug: string, name: string, status: string, date: datetime, repo: string>
# dev list --status open

# One property of a ticket.
export def query [
  slug: string@_slugs
  property: cell-path@_properties
  --repo (-r): string@_repos
]: nothing -> any
# dev query hooks-placement ticket.outcome   # singular

# Change a ticket and rewrite its file canonically; returns the path.
export def edit [
  slug: string@_slugs
  --repo (-r): string@_repos
  --set: record # Merged into `ticket` (D14)
  --add-task: record # A `[[tasks]]` row, created in Todoist first; `labels` defaults to [] and `completed` to false
  --complete: list<string> # Task contents to complete, in Todoist first
]: nothing -> path
# dev edit hooks-placement --set {status: open}

# Scaffold a v4 ticket file; returns the path.
export def new [
  slug: string
  --repo (-r): string@_repos # Target repository; defaults to the registered repository containing the cwd
  --name (-n): string # Defaults to the slug with - and + as spaces, title-cased
  # ... the rest of the signature is D5
]: nothing -> oneof<path, nothing> # nothing when --edit has opened the file (D5)
# dev new tri-sync --name "Tri-sync" --edit

# Convert v3 issue files (docs/issues/<slug>.issue.toml) into v4 ticket files (docs/tickets/<slug>.toml).
export def migrate [
  ...slugs: string@_v3-slugs
  --all (-a)
  --dry-run (-d) # Report without writing
  --repo (-r): string@_repos
]: nothing -> table<slug: string, from: path, to: path, changed: bool>
# dev migrate --all --dry-run
```

## Behaviour

- Discovery: every row of `$env.repo.path` (`table<name owner directory>`, the registry the sibling
  `repo` module keeps; `repo push` extends it, `repo list` shows it) contributes
  `<directory>/docs/tickets/*.toml`; the slug is the file stem. A slug in two repositories errors (D3)
  unless `--repo` names one.
- `dev` opens the file and checks `version`, the required keys and types above, the `status` enum,
  the slug charset (D13), that `ticket.slug` equals the stem, that each row carries at most one label
  starting with `-` and that it is `-human`, `-agent` or `-mixed`, and parses `ticket.date` with
  `into datetime`. The returned record is the document with `date` as a datetime.
- `--md` renders, in order: `# <name>` (`# <slug>` when `name` is absent), the outcome paragraph,
  `## Requirements` and `## Constraints` as bullet lists, `## Output` and `## Landscape` as `to md`
  tables, `## Bindings` as bullets `- <kind>/<type>: <item>`, `## Tasks` as `- [ ] <content>` and
  `- [x] <content>` lines, one per row. Empty sections are omitted. This is the remote issue body;
  `dev sync` owns it outright, hand edits to the body are overwritten, discussion goes in comments.
  The one thing read back from it is the box state of a `## Tasks` line whose text equals a row's
  `content` (Ownership; bindings document D8).
- `list` returns one row per file, sorted by `date` descending then `slug`; `--status` and `--repo`
  filter.
- `query` is `dev <slug> | get <property>`.
- The writer, shared by `edit`, `new` and `migrate`: rebuild the record in canonical order (top-level
  keys, then each row's and nested record's keys per the Schema table), compact nulls, format `date` with `format date %F`, `to toml`, save to
  `mktemp --tmpdir-path <dir> --suffix .toml` in the file's own directory (so the final step is a
  rename, not a copy), `mv --force` over the target. Writing an unchanged record yields identical bytes.
- `edit` applies `--set` (D14), appends the `--add-task` row, sets `completed = true` for every
  `--complete` content, then writes. `--add-task` and `--complete` are the only write paths from the
  file side to Todoist, because Todoist owns the rows (D1): `--add-task` runs
  `todo add <content> --parent id:<reference.todoist.id>` (plus `--description` and `--labels` when
  the row carries them) and `--complete` finds each content among `$td_task`'s subtasks and runs
  `todo done`, then the local write happens. Both require `ticket.reference.todoist` (message under
  Validation) and ship with `dev sync` (Phase 5a of the plan); until then they raise that error and
  nothing else.
- `new` writes `version`, `name`, `slug`, `date` (today), `status = "draft"`, `outcome = ""`,
  `requirements = []`, `constraints = []` through the writer, after checking the slug (D13) and that
  the file does not exist. `--interactive` prompts, in this order, `name` (`--default` the derived
  name), `outcome`, `requirements` and `constraints`; the two lists take one item per line (Enter
  submits, Alt+Enter or Shift+Enter inserts a line), blank lines dropped; `slug`, `date`, `status`
  and `version` are never prompted, and `target` and `extends` are set with `edit --set`.
  `--interactive` and `--prompt` are exclusive. `--prompt` runs
  `claude -p --session-id <uuid>` with a fresh `random uuid` and `--files` as context, saves the reply
  to `$nu.temp-dir/dev-new-<slug>-<uuid>.toml`, validates it with the checks listed under `dev`, then
  writes; the uuid in the file name is the only state kept. `--recover <file>` alone validates and
  writes that file without a model call; with `--prompt` it runs `claude -p --resume <uuid>` with the
  new prompt and validates the new reply the same way. (`claude` 2.1.278: `-p/--print`,
  `--session-id <uuid>`, `-r/--resume <session-id>`, verified 2026-09-18.)
- `migrate` reads `docs/issues/<slug>.issue.toml` (its completer lists those files), refuses
  `version != "3.0.0"` and every refused path below naming the offending path, maps every other leaf per
  the table, drops the v3 `[tasks]` table (D2), writes `docs/tickets/<slug>.toml` through the writer
  and removes the source (D15). A source whose target already exists errors. `--dry-run` returns the
  same rows and writes nothing.
- Apart from `edit --add-task`/`--complete`, none of the six commands runs `git`, `gh` or `td`; they
  read and write local files. Every other remote-host and Todoist call belongs to `dev sync`.
  `new --prompt` is the only command that calls `claude`.

## Validation and error copy

| condition                                    | message |
|----------------------------------------------|---------|
| no registered repository has ticket files    | `no ticket files under docs/tickets in the registered repositories; run repo push <dir> to register one or dev new <slug> to create one` |
| unknown slug                                 | `no ticket named '<slug>' in the registered repositories; run dev list to see them` |
| slug in several repositories (D3)            | `slug '<slug>' found in repos <a>, <b>; pass --repo` |
| `--repo` not registered                      | `no registered repository named '<repo>'; run repo list to see them` |
| `version = "3.0.0"`                          | `'<path>' is version 3.0.0; move it to docs/issues/<slug>.issue.toml, then run dev migrate <slug>` |
| other version                                | `'<path>' is version '<v>'; only "4.0.0" loads and "3.0.0" migrates; edit <path> then re-run dev <slug>` |
| required key missing                         | `'<path>' is missing <key>; edit <path> then re-run dev <slug>` |
| wrong type                                   | `'<path>': <key> must be <type>, got <type>; edit <path> then re-run dev <slug>` |
| bad status                                   | `'<path>': status must be one of draft, open, done, aborted, got '<x>'; edit <path> then re-run dev <slug>` |
| slug mismatch                                | `'<path>': ticket.slug is '<x>' but the file is named '<stem>'; rename one, then re-run dev <slug>` |
| bad slug on load (D13)                       | `'<path>': '<x>' is not a slug: use lowercase letters, digits, - and +, no dots; rename the file and ticket.slug, then re-run dev <slug>` |
| unparsable date                              | `'<path>': ticket.date '<x>' is not a date; write "YYYY-MM-DD", then re-run dev <slug>` |
| bad attribution label                        | `'<path>': task '<content>' has label '<x>'; a label starting with - must be one of -human, -agent, -mixed, at most one per task; edit <path> then re-run dev <slug>` |

## Naming

Exported names are `main`, `list`, `query`, `edit`, `new`, `migrate` (and `sync` from the sync spec).
A module's exported names are predeclared before its imports are parsed, so an exported `update`,
`rm`, `find`, `get` or `export` would shadow the builtin inside `util`, `todo`, `repo` or `completion`
and break their parse (verified 2026-09-15 with a scratch module pair, in both statement orders).
`edit` and `list` are safe because neither names a builtin (`which edit list` resolves `edit` to an
external and `list` to nothing; `todo` exports both). Run the ide-check command below after adding
every export.

# `dev sync`: bindings

What the existing design already commits `dev sync` to. Collected on 2026-09-18 from
`dev/docs/2026-09-15_dev-core.spec.md` (intro, D1, D2, D12, D13, D14, schema, `edit` bullets,
Validation), `dev/docs/_design/05-plan.md` (Phase 0, D6 to D9, Phases 3b, 4, 5a,
5b, 6), `dev/docs/_design/06-ownership.d2`, `dev/docs/_design/07-lifecycle.d2`, and the live Todoist
probes of 2026-09-16 and 2026-09-18 named inline. The sync spec (`dev/docs/<date>_dev-sync.spec.md`,
written in Phase 4 of the plan) supplies the contract, the algorithm and the error copy; it may not
weaken a line below without amending the document that binds it.

"The remote host" is the issue tracker of the repository's git remote (core spec intro): issues,
milestones, issue state and Markdown bodies only; GitHub through `gh` is the one host wired.

## Ownership

Each key has one owner; sync moves data only in the stated direction (core spec intro, `06-ownership.d2`).

| datum                                                  | owner        | sync direction |
|--------------------------------------------------------|--------------|----------------|
| ticket existence, `content` = slug                     | Todoist      | Todoist -> file (`reference.todoist`), Todoist -> remote (issue title) |
| kind label `%deliverable` / `%actionable`              | Todoist      | set once by sync at creation (D1: `%deliverable` when `[[ticket.output]]` is non-empty, else `%actionable`); never read back, never stored |
| task rows (direct subtasks of the ticket task)         | Todoist      | Todoist -> file (`[[tasks]]` wholesale) -> remote (`## Tasks` checklist, write-only) |
| reopening                                              | Todoist      | Todoist -> file (`status = open`) -> remote (reopen issue) |
| body: `outcome requirements constraints output scope landscape bindings extends` | file | file -> remote (issue body = `dev <slug> --md`) |
| `status`                                               | file         | file -> Todoist (check on `done`/`aborted`), file -> remote (close with reason); closure also flows in from either remote surface (D6) |
| `target`                                               | file         | file -> remote (milestone assignment), file -> Todoist (arrow line on the version-target task) |
| `reference.todoist {id url}`, `reference.remote {index url branch}` | sync | written through the `edit` writer, never hand-edited |
| ticket task description, first line                    | sync         | the D12 link line; later lines are the user's |
| version-target task description, first line            | sync         | the arrow line `→ <repo>#a #b …`; later lines are the user's |
| issue body                                             | sync         | overwritten on every sync; discussion lives in comments |
| Todoist labels `%deliverable %actionable -human -agent -mixed` | sync | created when missing (core spec, Decisions preamble) |

## Identity and linking

- One name on every surface: the slug (D13, `^[a-z0-9]+([+-][a-z0-9]+)*$`) is the Todoist task
  `content`, the issue title, the git branch and the file stem. Identity is `repo` + slug (D3).
- First link: search every Todoist project for `content` = slug, open tasks then completed ones
  (`07-lifecycle.d2` s3); more than one match is an error; a match outside the repository's mapped
  project is linked and reported (plan D7).
- After the first link, matching is by `reference.todoist.id` only, never by content (D13, plan D7).
- The mapped project is the one named after the repository, then each alias on the repository's
  `$env.repo.path` row in order (`project` or `project/section`; plan Phase 3b). A missing project
  is an error naming `td project add <repo>` (plan D7).
- Tasks carrying a `?` label are skipped (plan D7). The user's live convention (2026-09-17): `?seed`
  marks a task defined elsewhere (an issue, a v3 file) that still needs porting into dev's shape,
  `?stub` one with no definition anywhere yet; dropping the label is how a task enters sync.
- A `done` or `aborted` ticket with no `reference.todoist` gets no task created (plan D7).
- `draft` tickets get the Todoist leg (so rows can be captured from the phone) and skip the remote leg
  (plan D6, `07-lifecycle.d2` s3).

## Todoist leg

- The ticket task is created with `todo add <slug> --project <mapped> --labels [<kind>]` when the
  first link finds nothing (`07-lifecycle.d2` s3).
- Rows: the task's direct subtasks, one tier, in Todoist order, mirrored wholesale into `[[tasks]]`
  as `{content, description?, labels, completed}` on every sync (D1). `labels` keeps at most the one
  attribution label (`-human`, `-agent`, `-mixed`); any other label on a subtask is not mirrored.
  Reads: `todo list --parent id:<id>` plus `todo list --completed --parent id:<id>`; completed reads
  cover a three-month window (plan Phase 0, `td completed list`).
- Description: the first line is `[<slug> · Issue #<index> · <owner>/<repo>](<url>)` from
  `reference.remote` (live format, probe 2026-09-18). Sync replaces the first line when it already is
  such a link, otherwise prepends the link above the existing text; every later line is left alone; a
  ticket without `reference.remote` gets no description write (D12).
- Closure in: a checked ticket task sets the file's `status = done` (or `aborted` when the file
  already says so) and closes the issue (D6, `07-lifecycle.d2` s6). Closure out: `status = done`
  checks the task; `status = aborted` checks the task and closes the issue as not planned (s6 abort).
- Reopen in: an unchecked task on a `done`/`aborted` ticket sets `status = open` and reopens the
  issue (D6). This is the only reopen path.

## Write-through from `dev edit`

The two commands that reach Todoist from the file side (core spec, `edit` bullets; plan Phase 5a):

- `dev edit <slug> --add-task {content, description?, labels?}` runs
  `todo add <content> --parent id:<reference.todoist.id>` (with `--description` and `--labels` when
  given), then writes the row locally with `labels` defaulting to `[]` and `completed` to `false`.
- `dev edit <slug> --complete [<content> …]` finds each content among the ticket task's subtasks and
  runs `todo done` on it, then sets `completed = true` locally. Unknown content:
  `no task '<content>' in '<slug>'; run dev query <slug> tasks to list them`.
- Both require `reference.todoist`; without it: `'<slug>' has no Todoist task yet; run dev sync <slug> first`.
  Until Phase 5a lands, that error is their whole implementation (plan Phase 2 step 5).
- Every `td` call goes through the `todo` module, never `^td` (plan Phase 5a verification grep).

## Remote leg

- Skipped while `status = draft` (D6).
- Ensure the issue exists with title = slug and body = `dev <slug> --md` (core spec `--md`: `# <name>`
  or `# <slug>`, outcome, `## Requirements`, `## Constraints`, `## Output`, `## Landscape`,
  `## Bindings`, `## Tasks` checklist; empty sections omitted); the body is rewritten whenever it
  differs (plan D8, Phase 4).
- State per `status`: `open` open; `done` closed, reason completed; `aborted` closed, reason not
  planned (D6). An issue found closed while the file says `open` sets the file (`done` for
  completed, `aborted` for not planned) and checks the Todoist task (`07-lifecycle.d2` W3). An issue
  found open while the task is checked is reported, not applied (D6).
- `reference.remote` is `{index, url, branch}`; `branch` is set to the slug on first create and no git
  branch is created (D6). Index is parsed from the URL as in `~/.local/share/nupm/modules/issue/mod.nu:209-213`.
- The host is never read for rows; the checklist is write-only (D8).
- Wired calls (plan Phase 0, `gh` 2.100.0): `gh issue create -R owner/repo -t <title> -F -`,
  `gh issue edit <n> -R owner/repo -F -`, `gh issue view <n> -R owner/repo --json number,url,state,title,body`,
  `gh issue close <n> -R owner/repo --reason {completed|"not planned"}`, `gh issue reopen <n> -R owner/repo`.
  Every `gh` call goes through one private wrapper using `elevate with-auth --login {|| ^gh auth login } gh …`
  that errors with stderr (plan Phase 5b); the error shape to copy is `repo/mod.nu:304-318`.

## Version targets

- `ticket.target` is a release target such as `"v0.4.0"`; the live names carry the `v`, and a target
  need not be a version (`daisy-thesis@literature_review_draft`, probe 2026-09-18). The file owns
  membership; sync projects it (core spec schema).
- Todoist side: the task `<repo>@<target>` in the parent project of the repository's project
  (`parentId` in `td project list --json`, probe 2026-09-18). Live labels on those tasks
  (`^next ^upcoming`, `:ready :blocked`, `#plugin #mcp #application #interface #documentation`,
  `?stub`) are the user's; sync never sets or reads them.
- Missing version-target task: an error naming the task and `dev sync <slug> --create-target`; with
  the flag, sync creates `<repo>@<target>` in that parent project with no section and no labels, then
  continues (plan D8).
- Remote side: ensure the milestone titled `<target>` exists, creating it when missing, with state
  from the version-target task's checked flag and due date from its due date; assign the issue to it
  (plan D8, Phase 4). A checked version-target task with open member tickets closes the milestone
  and leaves the issues assigned; both sides allow that (`07-lifecycle.d2` W5).
- The version-target task's description keeps an arrow line `→ <repo>#a #b …` listing the member
  issues, maintained under the D12 rule: replaced when the first line already is an arrow line,
  otherwise prepended (plan D8).
- A renamed version-target task (`nu-fluency@v0.4.0` to `@v0.4.1`) is the missing-task case above:
  error row, nothing written (`07-lifecycle.d2` W5).

## Command surface bound so far

`dev sync [...slugs: string@_slugs --all --dry-run --create-target --skip: list<string> = []]:
nothing -> table<slug todoist remote milestone result>` (plan Phase 4). `--skip` accepts `todoist`,
`remote`, `milestone`. Every leg is a sequence of "ensure" steps so a second run is a no-op, and
`--dry-run` reports per leg what would change. Auth retry through `elevate with-auth` at most once per
leg. `reference` is written per leg with any skip recorded in the result row (plan Phase 5b guard).
Exported name `sync` (core spec, Naming; do not export `update`, `rm`, `find`, `get`, `export`).

## Breakdowns and their required outcome

Traced in `07-lifecycle.d2`; every case ends in a result row or an error message, never a repair
that was not asked for.

| case | required outcome |
|------|------------------|
| W1 task renamed in Todoist (`content` != slug) | error row "content drifted", nothing written |
| W2 task deleted or moved out of every mapped project | error row "task gone: set aborted or clear the reference", nothing written; auto-abort is not in this version |
| W3 issue closed on the host first (PR "closes #N") | accepted: task checked, `status = done`; the not-planned reason maps to `aborted` |
| W4 half a sync (Todoist leg ok, remote leg fails) | result row names the failed leg and the next command; the next run's Todoist ensure steps find nothing to do |
| W5 version-target task renamed or checked early | renamed: the missing-task error above; checked early: milestone closed, issues stay assigned |
| issue reopened on the host while the task is checked | reported, not applied (D6) |
| `?`-labelled task | skipped (plan D7) |
| slug found in more than one project at first link | error (plan D7) |
| slug found outside the mapped project | linked, placement reported (plan D7) |
| mapped project missing | error naming `td project add <repo>` (plan D7) |
| target set, version-target task missing | error naming `--create-target` (plan D8) |

## Tests bound

Offline (no network): the D6 closure/reopen decision as a pure function over
`(status, task checked, issue state)`; the row diff from fake `todo list` rows to the `[[tasks]]`
mirror and closure action; `dev <slug> --md` body equality for a fixture; the milestone decision
(create/assign/state) from fake `gh api` rows; `dev sync alpha --dry-run --skip [remote milestone]`
with no Todoist project errors naming `td project add` (plan Phases 5a, 5b).

Live, opt-in with `DEV_SYNC_WRITE=1` (the `TODO_TEST_WRITE` pattern at `todo/tests/suites/todo.nu:27`):
a scratch ticket synced twice into a scratch Todoist project reports no changes the second time;
`edit --add-task` then `edit --complete` round-trip; cleanup with `todo rm`. No scratch remote
repository: the remote legs are verified by the user with `--dry-run` against a real issue, then one
real sync on a ticket of their choosing (plan D9, Phase 5b).

# `dev sync`: decisions and bindings

What the design already commits `dev sync` to, ahead of its spec. Written 2026-09-18 from
`dev/docs/2026-09-18_dev-core.spec.md` (the core spec: Ownership, D1, D2, D12, D13, D14, Schema,
Behaviour, Validation), the decisions D6 to D9 below (settled in chat on 2026-09-17/18),
`dev/docs/_design/06-ownership.d2`, `dev/docs/_design/07-lifecycle.d2`, and the live Todoist probes
named inline. The sync spec (`dev/docs/<date>_dev-sync.spec.md`, Phase 4 of
`dev/docs/_design/05-plan.md`) supplies the contract, the algorithm and the error copy; it may not
weaken a line below without amending the document that binds it. Where this document and the core
spec differ on anything sync does, this document wins; on everything else the core spec wins.

Vocabulary is the core spec's: "the remote host" is the issue tracker of the repository's git remote
(issues, milestones, issue state, Markdown bodies; GitHub through `gh` is the one host wired);
`$td_task` is the ticket's Todoist task, `$td_subtask` one of its direct subtasks.

## Scope

Mandatory reading before any sync work (the core spec's intro says the same). `dev sync` is the only
command that talks to more than one surface, so its edge is drawn here once; a claim elsewhere that
sync does something not listed under "does" is wrong, and a claim that it may do something listed under
"never does" is wrong.

`dev sync` does, per ticket:

- link the ticket to its Todoist task (`reference.todoist`), creating `$td_task` with the kind label
  when no task exists (D7);
- apply a box ticked or unticked on the remote issue's `## Tasks` checklist to the matching
  `$td_subtask`, then mirror `$td_task`'s direct subtasks into `[[tasks]]` (D8, D1; a completed row
  the reads no longer return is kept);
- move closure and reopening between surfaces as D6 states, writing `status` when it does;
- write its one description line on `$td_task` and on the version-target task (core spec D12);
- ensure the remote issue exists, its body equals `dev <slug> --md`, its state matches `status`, and
  it is assigned to the milestone named by `target`; write `reference.remote` (D8);
- ensure the milestone named by `target` exists with state and due date from the version-target task
  (D8); create the version-target task only under `--create-target`;
- report every drift case in the Breakdowns table as a result row or an error.

`dev sync` never does:

- create a Todoist project (the error names `td project create --name <repo>`), a git branch, a commit, or a
  pull request (`gh issue develop` included);
- read the host for anything but issue state and the box state of `## Tasks` lines; never for the
  title, body text, labels, assignees, comments, or which checklist lines exist;
- read the kind label back, or set or change sections, priorities, due dates, or any label on
  `$td_task`, a subtask, or the version-target task, beyond the kind label at creation, the
  attribution label on `edit --add-task`, and the section a `project/section` alias names at
  creation (D7); the only label reads are a `?` label on `$td_task` (D7) and a row's attribution
  label (D1), the only section read is the one that alias names, and the version-target task is read
  only for its checked flag and due date (D8);
- change a row's content, description, labels or order from any surface but Todoist; `edit --add-task`
  and `edit --complete` are `dev edit`'s write paths, not sync's;
- change the ticket body or `target`; change `status` other than the D6 closure and reopen cases;
- touch any description line but its own first line;
- repair drift: rename, move or re-create a task, clear a reference, or reassign a project;
- delete anything on any surface: no task, subtask, issue, milestone, label or file;
- create a label: every label it attaches (`%deliverable`, `%actionable` at task creation; the
  attribution label on `edit --add-task`) must be in `todo labels` first, else an error naming
  `td label create --name=<name>` (`td label create` takes no positional);
  `td task add --labels <x>` accepts any string silently and attaches it as a shared label without
  creating one (probe 2026-09-19; `-agent` and `-mixed` were created that day, so all three
  attribution labels now exist);
- cache state between runs: every ensure step reads its surface before it writes (the plan's
  no-cache rule, Phase 0 anti-patterns).

## Decisions

Numbered to continue the core spec's D1 to D15.

- **D6: status, closure and reopening.** `draft` skips the remote leg (the Todoist leg still runs so
  rows can be captured from the phone). `open` keeps the issue open; `done` closes it with reason
  completed and checks `$td_task`; `aborted` closes with reason not planned and checks `$td_task`.
  Closure is accepted from any surface: a checked `$td_task` or a closed issue found by sync sets the
  file's `status` (`done` for completed/checked, `aborted` for not planned) and propagates to the
  remaining surface. Reopening is accepted from Todoist only: unchecking `$td_task` on a `done` or
  `aborted` ticket sets `status = open` and reopens the issue; an issue reopened on the host while the
  task is checked is reported, not applied. `dev edit --set {status: open}` on a ticket whose
  `$td_task` is still checked is reverted to `done` by the next sync and reported as a result row
  (Todoist owns reopening). The checked flag, the current `content` and deletion are read with
  `todo --json --long task view id:<id> --full`: only `--full` carries `checked`, `completedAt` and
  `isDeleted`, and `todo view` drops them (`todo/mod.nu:57,233-245`; probe 2026-09-19).
  `reference.remote.branch` is set to the slug when the issue is created; no git branch is created.
- **D7: the Todoist model.** The ticket is one task, `content` = slug, in the project named after the
  repository or one of its aliases (Phase 3b of the plan); resolution tries the repository name, then
  each alias in order (`project` or `project/section`); a `project/section` alias scopes the first-link
  search and the creation of `$td_task` to that section (`td task add --section` exists; `td task
  list` has no section flag, so the search filters on the raw row's `sectionId`, which `todo list`
  drops today: Phase 3b adds `--section` to `todo list` and `todo add`, and how much section handling
  is worth is gauged there, once the three name-matched repositories sync; ruling 2026-09-19); a
  missing project is an error naming `td project create --name <repo>` (`td project` has no `add`).
  First link searches every project for `content` = slug, open tasks then
  completed ones; more than one match is an error; a match outside the mapped project is linked and
  reported. Afterwards everything is matched by `reference.todoist.id`, never by content. `[[tasks]]`
  is `$td_task`'s direct subtasks, mirrored on every sync (D1, Todoist leg); local edits reach Todoist
  only through `edit --add-task` and `edit --complete`, host-side box toggles only through the D8
  read-back. The kind label is set once at creation and is
  Todoist's afterwards (D1). Tasks carrying a `?` label are skipped: by the user's convention
  (2026-09-17) `?seed` marks a task defined elsewhere (an issue, a v3 file) still to be ported into
  dev's shape, `?stub` one with no definition anywhere yet, and removing the label is how a task
  enters sync. A task deleted (`isDeleted` in the `--full` view: a deleted task still resolves by
  id, while an unknown id is an HTTP 400 error, probe 2026-09-19), moved out of every mapped project,
  or whose `content` no longer equals the slug is reported, never repaired (auto-abort waits for
  usage to prove the need). A `done` or
  `aborted` ticket with no `reference.todoist` gets no task created.
- **D8: the remote projection, checkbox read-back, and version targets.** The issue body is
  `dev <slug> --md` and is sync-owned: hand edits are overwritten, discussion lives in comments. The one
  thing read back from the body is the box state of the `## Tasks` lines (user ruling 2026-09-18):
  a line `- [ ] <text>` or `- [x] <text>` (`[X]` accepted) matches the row whose `content` equals
  `<text>` exactly; a text matching no row, or matching two, is ignored. The file's `[[tasks]]` row is
  the state at the last sync, so with `H` the host's box, `T` the subtask's current state in Todoist
  and `M` the mirror, all booleans: `H != M` and `T == M` (the host moved, Todoist did not) applies
  `H` to Todoist (`todo done` or `todo reopen` on `$td_subtask`); every other case applies nothing,
  because `T != M` means Todoist already moved and, with two states, moved to `H`, so a conflict
  between `H` and `T` cannot occur (2026-09-19 review; the earlier "Todoist wins a conflict" branch was
  unreachable). Lines added, removed or reworded on the host are never read; the body is rewritten
  from Todoist after the toggles are applied, so the rewritten checklist already reflects them. `ticket.target = "<target>"` (live shape `v0.4.0`; a
  target need not be a version) names the Todoist task `<repo>@<target>` in the parent project of the
  repository's project and the remote milestone titled `<target>`. Sync ensures, on every run, that
  the milestone exists, that its state matches the version-target task's checked flag and its due
  date the task's due date (creating it when missing), assigns the issue to it, and maintains the
  arrow line as the first line of the version-target task's description under the D12 rule. The arrow
  line is `→ <repo>#a #b …`: a literal `→`, one space, then the member issues as `<repo>#<index>`
  joined by single spaces in ascending index order; it is replaced when the first line matches
  `^→ \S+#\d+( \S+#\d+)*$`, otherwise prepended, never touching a hand-written line. A
  missing version-target task is an error naming the task and `dev sync <slug> --create-target`; the
  flag is accepted with exactly one slug (with `--all` or several slugs it errors) and creates
  `<repo>@<target>` in that parent project with no section and no labels (the user curates those),
  then continues; a renamed target task is repaired by the user (rename it back, or set the new
  `target`), never by the flag.
- **D9: live tests are opt-in and own their Todoist project.** The Todoist leg's live tests are
  gated by `DEV_SYNC_WRITE=1` (the `TODO_TEST_WRITE` pattern at `todo/tests/suites/todo.nu:27`) and
  run inside a fixture: setup creates the project `dev-sync-test` (`todo project create --name
  dev-sync-test`, the passthrough; `td project` has no `add`) and errors if a project of that name
  already exists rather than reuse it; teardown runs `todo rm` on every task the run created, then
  `todo project delete id:<id> --yes` (which refuses a project with open tasks); every name the tests
  use is hardcoded (`dev-sync-test`, slugs `dev-sync-alpha` and `dev-sync-beta`) so no run can touch
  real data (ruling 2026-09-19). No scratch remote repository is named: the remote legs are verified
  by the user with `--dry-run` against a real issue, then one real sync on a ticket of their choosing.

## Ownership

Each datum has one owner; sync moves it only in the stated direction (core spec, Ownership;
`06-ownership.d2`).

| datum                                                  | owner   | sync direction |
|--------------------------------------------------------|---------|----------------|
| ticket existence, `content` = slug                     | Todoist | Todoist -> file (`reference.todoist`), Todoist -> remote (issue title) |
| kind label `%deliverable` / `%actionable`              | Todoist | set once by sync at creation (D1); never read back, never stored |
| task rows (direct subtasks of `$td_task`)              | Todoist | Todoist -> file (`[[tasks]]`; completed rows outside the read window kept) -> remote (`## Tasks`); a box toggled on the host flows remote -> Todoist first (D8) |
| box state of a `## Tasks` line                          | Todoist | remote -> Todoist when it differs from the mirror and Todoist has not moved (D8); never file -> remote on its own, the line is rendered from the row |
| reopening                                              | Todoist | Todoist -> file (`status = open`) -> remote (reopen issue) |
| body: `outcome requirements constraints output scope landscape bindings extends` | file | file -> remote (issue body) |
| `status`                                               | file    | file -> Todoist (check on `done`/`aborted`), file -> remote (close with reason); closure also flows in from either remote surface (D6) |
| `target`                                               | file    | file -> remote (milestone), file -> Todoist (arrow line) |
| `reference.todoist {id url}`, `reference.remote {index url branch}` | sync | written through the core spec's writer, never hand-edited |
| first description line of `$td_task`                   | sync    | the D12 link line; later lines are the user's |
| first description line of the version-target task      | sync    | the arrow line; later lines are the user's |
| issue body                                             | sync    | overwritten on every sync |
| labels `%deliverable %actionable -human -agent -mixed` | user    | curated by the user; sync checks `todo labels` before attaching one and errors on a missing name (Scope) |
| version-target labels `^next ^upcoming :ready :blocked #plugin #mcp #application #interface #documentation ?stub` | user | never set or read by sync (live probe 2026-09-18) |

## Todoist leg

- Ticket task creation: `todo add <slug> --project <mapped> --labels [<kind>]` when the first link
  finds nothing (`07-lifecycle.d2` s3).
- Rows: `$td_task`'s direct subtasks, one tier, mirrored into `[[tasks]]` as
  `{content, description?, labels, completed}` on every sync; `labels` keeps at most the one
  attribution label, any other subtask label is not mirrored (D1). `completed` is which read returned
  the row, since no read through `todo` carries a checked flag; order is the open rows in Todoist
  order, then the completed rows by completion date ascending. Reads: `todo list --parent id:<id>`
  for open rows; `todo list --completed --project <mapped> --since <today minus 90 days>` filtered on
  `parent == <id>` for completed ones (completed rows carry `parentId`, probe 2026-09-19), because the
  completed branch ignores `--parent` (`todo/mod.nu:38-43`) and `td completed list` has no parent
  filter; `--since` is always passed because `td` defaults it to today, and the API caps the window at
  three months (`td` 5.3.9). `todo view --full --include-children` returns open children only (probe
  2026-09-19), so it is no substitute for the completed read. The mirror is rebuilt from the two
  reads, except that a mirror row with `completed = true` that neither read returned (completed
  before the window, or deleted after completion) is kept as it is (ruling 2026-09-19); a mirror row
  with `completed = false` absent from both reads is dropped (deleted while open).
- Description: the first line is `[<slug> · Issue #<index> · <owner>/<repo>](<url>)` from
  `reference.remote` (live format, probe 2026-09-18), replaced when the first line matches
  `^\[<slug> · Issue #\d+ · [^\]]+\]\(https?://\S+\)$` (the slug literal, so no other line is ever
  replaced), else prepended; no write without `reference.remote` (D12).
- Closure in and out, reopen in: D6.

## Write-through from `dev edit`

The only file-side writes to Todoist (core spec, Behaviour; plan Phase 5a):

- `dev edit <slug> --add-task {content, description?, labels?}` (any other key is an error) runs
  `todo add <content> --parent id:<reference.todoist.id> --project <mapped>` (with `--description`
  and `--labels` when given; `--project` always, since whether a subtask inherits its parent's project
  is unprobed), then writes the row locally with `labels` defaulting to `[]` and `completed` to
  `false`.
- `dev edit <slug> --complete [<content> …]` finds each content among `$td_task`'s open subtasks
  (`todo list --parent id:<id>`) and runs `todo done`, then sets `completed = true` locally. Unknown
  content: `no task '<content>' in '<slug>'; run dev sync <slug>, then dev query <slug> tasks to list
  them`.
- With several flags in one call the Todoist calls run first, `--add-task` then `--complete`, and the
  file is written only after every call succeeds; a failure leaves Todoist ahead of the file, which the
  next `dev sync` mirrors.
- Both require `reference.todoist`; without it:
  `'<slug>' has no Todoist task yet; run dev sync <slug> first`. Until Phase 5a lands, that error is
  their whole implementation.
- Every `td` call goes through the `todo` module, never `^td` (plan Phase 5a verification).
- A box toggled on the host is the third row write path; it is `dev sync`'s (Remote leg, D8), not
  `dev edit`'s.

## Remote leg

- Skipped while `status = draft` (D6).
- Read the issue body once, parse the `## Tasks` lines and apply the D8 toggle rule to Todoist before
  the rows are mirrored.
- A ticket without `reference.remote` first searches
  `gh issue list -R owner/repo --state all --search 'in:title <slug>' --json number,title,state,url`
  for an issue whose title equals the slug exactly: one match is linked and reported, more than one is
  an error, none creates the issue.
- Ensure the issue exists with title = slug and body = `dev <slug> --md` (core spec, `--md`); the body
  is rewritten whenever it differs, compared after CRLF is normalised to LF (bodies edited in the web
  UI can come back with CRLF).
- State per D6. Index is parsed from the issue URL as in `~/.local/share/nupm/modules/issue/mod.nu:209-213`.
- Wired calls (`gh` 2.101.0): `gh issue create -R owner/repo -t <title> -b <body>` (prints the URL),
  `gh issue edit <n> -R owner/repo -b <body>` (also `--milestone`), `gh issue view <n> -R
  owner/repo --json number,url,state,title,body`, `gh issue close <n> -R owner/repo --reason
  {completed|"not planned"}`, `gh issue reopen <n> -R owner/repo`. The body travels as an argument,
  not stdin: every `gh` call goes through one private wrapper using
  `elevate with-auth --login {|| ^gh auth login } gh …` (`elevate/mod.nu:50`), whose signature is
  `nothing -> string` (no pipeline input); it errors with stderr, and the error shape to copy is
  `repo/mod.nu:304-318`.

## Version targets

D8, plus the live facts it rests on (probe 2026-09-18): version-target tasks are named
`<repo>@<target>` (`nu-fluency@v0.4.0`, `daisy-thesis@literature_review_draft`) and sit in the parent
project of the repository's project, resolvable through `parentId` in
`todo --json --long project list` (`todo projects` selects only `id name url`; the raw rows carry
`parentId`, probe 2026-09-19); a repository project with no parent is an error naming the project. A
renamed version-target task is the missing-task case (`07-lifecycle.d2` W5). A checked version-target
task with open member tickets closes the milestone and leaves the issues assigned; both sides allow
that (W5).

## Command surface bound so far

`dev sync [...slugs: string@_slugs --all --dry-run --create-target --skip: list<string> = []]:
nothing -> table<slug todoist remote milestone result>`. `--skip` accepts `todoist`, `remote`,
`milestone`; `--skip todoist` also skips the D8 read-back and renders `## Tasks` from the file's
mirror. Every leg is a sequence of "ensure" steps so a second run is a no-op; `--dry-run` reports per
leg what would change. Each leg's error is caught into that ticket's result row (W4); only a fatal
condition (no registered repository, `td` or `gh` absent) aborts a batch. The `elevate with-auth`
retry covers only `todo done`, `todo reopen` and `todo rm` (`todo/mod.nu:104-114`); `todo list`,
`todo view`, `todo add` and the `--json` passthrough take the plain path, so an auth failure there
surfaces as a `todo` error in the result row, and a non-interactive run never logs in
(`elevate/mod.nu:64-67`). `reference` is written per leg, with any skip recorded in the result row.
Exported name `sync` (core spec, Naming).

## Breakdowns and their required outcome

Traced in `07-lifecycle.d2`; every case ends in a result row or an error, never an unrequested repair.

| case | required outcome |
|------|------------------|
| W1 `$td_task` renamed (`content` != slug) | error row "content drifted", nothing written |
| W2 `$td_task` deleted (`isDeleted`) or moved out of every mapped project | error row "task gone: set aborted or clear the reference", nothing written |
| W3 issue closed on the host first (PR "closes #N") | accepted: task checked, `status = done` (`aborted` for not planned) |
| W4 half a sync (Todoist leg ok, remote leg fails) | result row names the failed leg and the next command; the next run's Todoist ensure steps find nothing to do |
| W5 version-target task renamed, or checked with open members | renamed: the missing-task error; checked early: milestone closed, issues stay assigned |
| issue reopened on the host while `$td_task` is checked | reported, not applied |
| `?`-labelled task | skipped |
| box toggled on the host, subtask unchanged in Todoist | applied to Todoist (`todo done` / `todo reopen`), then mirrored |
| subtask toggled in Todoist since the last sync, whatever the host shows | nothing applied to Todoist; mirrored (D8: a conflict cannot occur) |
| `dev edit --set {status: open}` while `$td_task` is checked | reverted to `done`, result row (D6) |
| auth failure on a leg (non-interactive, or after the one retry) | that leg's result row (W4) |
| `## Tasks` line matching no row, or two rows | ignored; rewritten from Todoist |
| slug found in more than one project at first link | error |
| slug found outside the mapped project | linked, placement reported |
| mapped project missing | error naming `td project create --name <repo>` |
| target set, version-target task missing | error naming `--create-target` |
| label to attach not in `todo labels` | error naming `td label create --name=<name>`, nothing written |

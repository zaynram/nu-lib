# `dev`: ticket files as the source of truth

Module `_internal/dev`.

Inspired by and replaces the nupm `issue` and `tasks` modules and the v3 `issue` schema with a new `ticket` schema.

Since the data structure for `ticket`s is mainly based on the `issue` data structure, the `ticket` schema
is the same as `v4` as referenced throughout this specification. Note that this implied succession is functionally symbolic.

One `<repo>/docs/tickets/<slug>.toml` per ticket is the only local store; there is no cache, index or mirror.

This spec covers the schema and the core commands (`dev`, `list`, `query`, `edit`, `new`, `migrate`).

For data synchronization, `dev sync` has its own spec.

## Decisions

Recorded as ponytail defaults. D1 to D5 come from the plan; D10 to D14 recorded on 2026-09-15
while drafting against the 14 shipped files (the audit had seen 9).

D1 - D14 rewritten manually (`zaynram`) on 2026-09-15 (~8pm).

For brevity, consider `$td_task` to represent an example Todoist task object for the sake of examples below.
Similarly, consider `$td_subtask` to represent an example subtask of `$td_task`.

- **D1:** v3 task object -> v4 task array

  ```toml
  # example of v3's task definition (digit-keyed objects)
  [tasks]
  0 = { id = 'string', target = 'string', completed = false, subtasks = [] }
  ```

  ```toml
  # example v4's proposed parent task definition (array element)
  [[tasks]]
    content = 'string' # $td_task.content
    labels = ['%deliverable'] # $td_task.labels
    completed = false # $td_task.completed != false
  ```

  ```toml
  # example of v4's proposed subtask definition (array element)
  [[tasks]]
    content = 'string' # $td_subtask.content
    description = 'string' # $td_subtask.description
    labels = [ # $td_subtask.labels
      '%actionable',
      '<attribution>'  # attribution ∈ {'-human', '-agent', '-mixed'} (optional; strict validation if present)
    ]
  ```

  > order: `%deliverable` precedes its `%actionable`s with tasks in the order received from Todoist data
- **D2:** no task migration support, only issue->ticket porting
  > Since `td` (Todoist CLI) is the source of truth for task data and all current tasks
  are already ported to Todoist, we are explicitly excluding any migration support from the
  current scope since all data points are derivable from task data alone.

  > For ticket porting, there are two files requiring manual edits: `nu-over-bash-hooks` and
  `polyglot-reference-autodoc-tooling`. The scope explicitly excludes a generic mapper implementation.
- **D3:** duplicate slugs are errors regardless of project/repository
  > A slug present in more than one registered repository errors; `--repo <name>` is the only
  disambiguator, on every command that takes a slug.
- **D4:** consistent quoted datetime value serialization on write operations
  > `date`s serialize to a quoted string in the format `"YYYY-MM-DD"` when writing
  to any files, with any value parseable with `into datetime` accepted on read.
- **D5:** `dev new --prompt` requires tight I/O contracts

  ```nu
  def "main new" [
    # ...
    --prompt (-p): string
    # Enables generation when passed; user prompt to submit for the generation
    --recover (-r): path
    # Saved reply to validate and write instead of generating; with `--prompt`, resume the reply's Claude
    # session with the new prompt (`claude -p --resume <id>`, the id is in the saved reply's file name)
    --files (-f): list<path> = [$EXAMPLE]
    # Files to include in the context for the generation; `const EXAMPLE: path = path self ./docs/example.toml` (the example file below)
    --edit (-e)
    # Open the written file with the `util editor` (custom `editor` definition from `util` sibling module)
    --interactive (-i)
    # Calls `input` per header with the following parameters:
    #  - (argument) $"(ansi bb)($head)(ansi rst) (ansi bd)($desc)(ansi w):(ansi rst) "
    #    - ANSI styling for separation of prompt text from user's input text
    #    - $head = The header name
    #    - $desc = Short description/criteria of what the input text should contain
    # - (option) `--history-file=<tempfile>`
    #    - History file for storing input from partial completion (include path in any errors/interrupts during wizard)
    # - (option) `--reedline`
    #    - Allows for multiline input; can be omitted since it is implied when using `--history-file` but listed here for transparency
    # - (option) `--suppress-output`
    #    - Disable printing of keystroke values
    # - (option) `--numchar=<int>`
    #    - Only passed for fields that have content length restrictions for saliency during entry
    #    - Protects from needing to rerun the wizard on length violations
    # - (option) `--default=<default>`
    #    - Only passed for fields that have a configured default value
    #    - Description should include the existence and showcase of the default value for saliency
    --continue (-c): path
    # Path to an `input` history file from an incomplete `--interactive` run; implies `--interactive`
  ]: [
    nothing -> error # If the raw reply TOML fails validation, include the relevant path to a tempfile (interactive history or saved generation reply) in the error
    nothing -> path # If the raw reply TOML passes validation, save it to the appropriate location and return the path
    nothing -> nothing # If `--interactive` and `--edit` are passed and validation succeeds, open the path in the editor and return nothing
  ] {
    # ...
  }
  ```

- **D10:** landscape differentiation becomes property-based and references are optional
  > v3 `issue.vision.landscape.internal[]` becomes a `[[ticket.landscape]]` row with `scope = "internal"`;
  a v3 `issue.vision.landscape.external[]` string becomes a row with `scope = "external"` and
  `synopsis = <string>`. `scope` is the only differentiator: every shipped row would have carried a
  `group` equal to its `scope`, so `group` is not part of v4.
- **D11:** flat bindings with property-based differentiation
  > v3 `[[issue.bindings.xabort]]` becomes `[[ticket.bindings]]` with properties `kind = "xabort"`,
  `item = action`, `type = trigger.mode` and the optional `conditions = trigger.conditions`
  (note: schema needs support for optional `conditions`). The `[[issue.bindings.xvalue]]` follows
  suit with `kind = "xvalue"`.
- **D12:** subtask `description` convention
  > The v3 `tasks.N.id` becomes absorbed by `%actionable`/`%deliverable` row's `description`. For projects within
  a GitHub repository, a `%deliverable` row's description should contain a markdown link referencing its GitHub issue URL
  and it's `%actionable` row's descriptions should contain markdown links referencing their respective GitHub subissues on
  the `%deliverable`'s issue.
- **D13:** extension becomes slug-based instead of path based
  > A v3 `extends` entry required a path (`docs/issues/<slug>.issue.toml`); v4 will store these as bare `<slug>`s
  since `<slug>`s in v4 will be universal references resolvable across Todoist (task content), GitHub (issue title),
  and local codebases (`ticket.slug` in TOML).
- **D15:** `dev migrate` moves files from `docs/issues` to `docs/tickets`
  > A v3 file is read from `docs/issues/<slug>.issue.toml`, written as `docs/tickets/<slug>.toml`
  and the source is removed; the migrate rows report both paths. Most tickets will be new rather
  than migrated.
- **D14:** local ticket editing will merge data using `--strategy=overwrite`
  > `dev edit --set` merges into `ticket` data with `merge deep --strategy=overwrite`;
  nested records merge, lists and scalars get replaced, so re-running the same `--set` is idempotent and
  `--set {constraints: []}` clears a list. `--add-task` is the append surface for the one list that
  grows.

## Schema

`version = "4.0.0"`, TOML 1.0 valid, depth at most 3, one shape per key. `dev edit` and `dev new`
build the record in this key order before `to toml`, so every write is canonical:

`version`, then `ticket` keys `name slug date status outcome requirements constraints extends output
scope landscape bindings reference`, then `tasks`.

| key                         | type                                                                                                             | required | notes |
|-----------------------------|------------------------------------------------------------------------------------------------------------------|----------|-------|
| `version`                   | string                                                                                                           | yes      | `"4.0.0"` |
| `ticket.name`               | string                                                                                                           | no       | Optional string to use as the "display name" of the ticket |
| `ticket.slug`               | string                                                                                                           | yes      | equals the file stem |
| `ticket.date`               | string                                                                                                           | yes      | written `"YYYY-MM-DD"`, read as datetime (see [D4](#decisions)) |
| `ticket.status`             | string                                                                                                           | yes      | one of `draft`, `open`, `done`, `aborted`; analogous with GitHub status |
| `ticket.outcome`            | string                                                                                                           | yes      | may be empty |
| `ticket.requirements`       | list<string>                                                                                                     | yes      | may be empty |
| `ticket.constraints`        | list<string>                                                                                                     | yes      | may be empty |
| `ticket.extends`            | list<string>                                                                                                     | no       | slugs |
| `[[ticket.output]]`         | `path` string, `purpose` string, `alias` string                                                                  | no       | `alias` optional |
| `[[ticket.scope.excluded]]` | `item` string, `deferred` string or bool                                                                         | no       | `deferred` optional |
| `[[ticket.landscape]]`      | `scope` in `internal`/`external`, `synopsis` string, `reference` string, `type` string, `incompatibility` string | no       | `reference`, `type`, `incompatibility` optional (see [D10](#decisions)) |
| `[[ticket.bindings]]`       | `kind` string, `item` string, `type` string, `conditions` list<string>                                           | no       | `conditions` optional (see [D11](#decisions)) |
| `[ticket.reference]`        | `github = {index int, url string, branch string}`, `todoist = {id string, url string}`                           | no       | tool-owned, written by `dev sync`, never hand-edited |
| `[[tasks]]`                 | `content` string, `description` string, `labels` list<string>, `completed` bool                                  | no       | pointers to Todoist tasks; a label starting with `-` is the attribution, one of `-human`, `-agent`, `-mixed`, at most one per row |

Absent optional keys read as an empty list (arrays of tables) or null (`extends`, `reference`, row-level optionals).

Keys with null values get compacted (`| compact`) at every level before writing, so a file never contains `"<Nothing>"`.

Example, `docs/tickets/hooks-placement.toml` after `dev migrate` (`[[tasks]]` rows appear once `dev sync` runs; their shape is in [D1](#decisions)). The same document ships as `dev/docs/example.toml`, the file `dev new --prompt` sends to the model:

```toml
version = "4.0.0"

[ticket]
name = "Hooks Placement Decision"
slug = "hooks-placement"
date = "2026-08-21"
status = "aborted"
outcome = "singular"
requirements = ["A definite stance with rationale, recorded where future contributors will find it."]
constraints = [
    "Gates nu-over-bash-hooks; no hook implementation before this freezes.",
    "Decision class is author-owned (manual).",
]

[[ticket.output]]
path = "docs/decisions/"
purpose = "Recorded decision: plugin-level hooks.json versus skill-scoped frontmatter."

[[ticket.scope.excluded]]
item = "Hook implementation"
deferred = "nu-over-bash-hooks"

[[ticket.landscape]]
scope = "internal"
synopsis = "No hooks shipped yet; placement undecided."
type = "greenfield"

[[ticket.bindings]]
kind = "xvalue"
item = "Freezing placement before implementation prevents rework across every future hook the plugin ships."
type = "sequencing-integrity"

[ticket.reference.github]
index = 5
url = "https://github.com/zaynram/nu-fluency/issues/5"
branch = "hooks-placement"
```

## Contracts

```nu
# Load and validate a ticket; `--md` renders the GitHub issue body instead.
export def main [
  slug: string@_slugs
  --repo (-r): string@_repos # Repository to look in when the slug exists in more than one
  --md # Render the ticket as the GitHub issue body (Markdown) instead of returning the record
]: nothing -> oneof<record, string>
# dev hooks-placement | get ticket.status   # aborted

# Tickets across the registered repositories.
export def list [
  --status (-s): string@_statuses
  --repo (-r): string@_repos
]: nothing -> table<slug: string, name: string, status: string, date: datetime, repo: string>
# dev list --status open

# One property of a ticket.
export def query [
  slug: string@_slugs
  property: cell-path@_properties
  --repo (-r): string@_repos
]: nothing -> any
# dev query hooks-placement ticket.outcome   # singular

# Change a ticket and rewrite its file canonically; returns the path.
export def edit [
  slug: string@_slugs
  --repo (-r): string@_repos
  --set: record # Merged into `ticket` (D14)
  --add-task: record # A `[[tasks]]` row; `labels` defaults to [] and `completed` to false
  --complete: list<string> # Task contents to mark completed
]: nothing -> path
# dev edit hooks-placement --set {status: open}

# Scaffold a v4 ticket file; returns the path.
export def new [
  slug: string
  --repo (-r): string@_repos # Target repository; defaults to the registered repository containing the cwd
  --name (-n): string # Defaults to the slug with dashes as spaces, title-cased
  # ... — See [D5](#decisions) for the rest of the parameter spec
]: nothing -> path
# dev new tri-sync --name "Tri-sync" --edit

# Convert v3 issue files (docs/issues/<slug>.issue.toml) into v4 ticket files (docs/tickets/<slug>.toml).
export def migrate [
  ...slugs: string@_v3-slugs
  --all (-a)
  --dry-run (-d) # Report without writing
  --repo (-r): string@_repos
]: nothing -> table<slug: string, from: path, to: path, changed: bool>
# dev migrate --all --dry-run
```

Behaviour:

- Discovery: every row of `$env.repo.path` (`name`, `directory`) contributes
  `<directory>/docs/tickets/*.toml`; the slug is the file stem. A slug in
  two repositories errors per D3 unless `--repo` names one.
- `dev` opens the file, checks `version`, the required keys and types above, the `status` enum, that
  `ticket.slug` equals the stem, that each task carries at most one label starting with `-` and that it
  is `-human`, `-agent` or `-mixed`, and parses `ticket.date` with `into datetime`. The returned record is
  the document with `date` as a datetime.
- `--md` renders, in order: a `# <name>` line (`# <slug>` when `name` is absent), the outcome paragraph, `## Requirements` and
  `## Constraints` as bullet lists, `## Output` and `## Landscape` as `to md` tables, `## Bindings`
  as bullets `- <kind>/<type>: <item>`, `## Tasks` as `- [ ]`/`- [x]` lines of `content`. Empty
  sections are omitted.
- `list` returns one row per file, sorted by `date` descending then `slug`; `--status` and `--repo`
  filter.
- `query` is `dev <slug> | get <property>`.
- `edit` applies `--set` ([D14](#decisions)), appends `--add-task`, sets `completed = true` for every
  `--complete` content, then rebuilds the record in canonical order, drops null keys, formats `date`
  with `format date %F`, runs `to toml`, saves to `mktemp --tmpdir-path <dir> --suffix .toml`
  in the file's own directory and `mv --force` over the original. Writing an unchanged record
  yields identical bytes.
- `new` writes `version`, `name`, `slug`, `date` (today), `status = "draft"`, `outcome = ""`,
  `requirements = []`, `constraints = []` through the same writer; `--interactive` and `--prompt`
  are exclusive. `--prompt` runs `claude -p --session-id <uuid>` with a fresh `random uuid`, saves
  the reply to `$nu.temp-dir/dev-new-<slug>-<uuid>.toml`, and validates it through the same loader
  before writing; the uuid in the file name is the only state kept. `--recover <file>` alone
  validates and writes that file without a model call; with `--prompt` it runs `claude -p --resume
  <uuid>` with the new prompt and validates the new reply the same way.
- `migrate` reads `docs/issues/<slug>.issue.toml` (its slug completer lists those files), maps every
  leaf per the table below, drops the v3 `tasks` table ([D2](#decisions): the tasks live in Todoist
  and `dev sync` writes them), refuses on any unmapped or D2-listed path, writes
  `docs/tickets/<slug>.toml` through the same writer and removes the source ([D15](#decisions)). A
  source whose target already exists errors. `--dry-run` returns the same rows and writes nothing.
- None of the six commands in this spec runs `git`, `gh` or `td`: they only read and write local
  files. Every GitHub and Todoist call belongs to `dev sync` (its own spec). `new --prompt` is the
  only command that calls `claude`.

## Validation and error copy

| condition                                           | message |
|-----------------------------------------------------|---------|
| no registered repository has ticket files           | `no ticket files under docs/tickets in the registered repositories; run repo push <dir> to register one or dev new <slug> to create one` |
| unknown slug                                        | `no ticket named '<slug>' in the registered repositories; run dev list to see them` |
| slug in several repositories (see [D3](#decisions)) | `slug '<slug>' found in repos <a>, <b>; pass --repo` |
| `--repo` not registered                             | `no registered repository named '<repo>'; run repo list to see them` |
| `version = "3.0.0"`                                 | `'<path>' is version 3.0.0; move it to docs/issues/<slug>.issue.toml, then run dev migrate <slug>` |
| other version                                       | `'<path>' is version '<v>'; only "4.0.0" loads and "3.0.0" migrates; edit <path> then re-run dev <slug>` |
| required key missing                                | `'<path>' is missing <key>; edit <path> then re-run dev <slug>` |
| wrong type                                          | `'<path>': <key> must be <type>, got <type>; edit <path> then re-run dev <slug>` |
| bad status                                          | `'<path>': status must be one of draft, open, done, aborted, got '<x>'; edit <path> then re-run dev <slug>` |
| slug mismatch                                       | `'<path>': ticket.slug is '<x>' but the file is named '<stem>'; rename one, then re-run dev <slug>` |
| unparsable date                                     | `'<path>': ticket.date '<x>' is not a date; write "YYYY-MM-DD", then re-run dev <slug>` |
| bad attribution label                               | `'<path>': task '<content>' has label '<x>'; a label starting with - must be one of -human, -agent, -mixed, at most one per task; edit <path> then re-run dev <slug>` |
| `query` unknown property                            | `no property <property> in '<slug>'; run dev <slug> to see the record` |
| `edit` without changes                              | `nothing to edit: pass --set, --add-task or --complete` |
| `--complete` unknown content                        | `no task '<content>' in '<slug>'; run dev query <slug> tasks to list them` |
| `new` file exists                                   | `'<path>' already exists; run dev edit <slug> or pick another slug` |
| `new` outside a repository                          | `the cwd is not inside a registered repository; pass --repo` |
| `new` both modes                                    | `pass either --interactive or --prompt` |
| `new --prompt` bad reply                            | `the reply is not a v4 document (<reason>); reply saved to <tmp>; fix it and run dev new <slug> --recover <tmp>, or add --prompt '<correction>' to ask the same session again` |
| `--recover` file missing                            | `no saved reply at '<file>'; run dev new <slug> --prompt '<prompt>' to generate one` |
| `migrate` target exists                             | `'<to>' already exists; remove it or '<from>', then re-run dev migrate <slug>` |
| `migrate` refused path (D2 or unmapped)             | `'<path>': <v3 path> is not mapped by dev migrate; edit <path> then re-run dev migrate <slug>` |
| `migrate` without target                            | `pass one or more slugs or --all` |

Every message names the file or the next command; none refers to a flag that does not exist.

## Tests

`dev/tests/mod.nu` is the seam (module, `std/assert`, the runner's `skip`); suites live in
`dev/tests/suites/dev.nu` and run with `test dev/tests/suites`. `before each` creates a scratch
repository directory with `docs/tickets` and returns its root; each test sets `$env.repo` to that one
row first.

Phase 2 (schema, `dev`, `list`, `query`, `edit`):

- `dev list` on an empty repository returns `[]`.
- A hand-written v4 fixture `alpha.toml` loads: `dev alpha` returns the record, `date` is a
  datetime, `status` validated.
- `dev query alpha ticket.outcome` returns the string; an unknown property errors naming `dev alpha`.
- `dev edit alpha --set {status: open}` returns the path and the file re-reads with `status = "open"`;
  `--add-task` appends a row with defaults; `--complete` flips `completed`.
- Editing twice yields identical bytes (`open --raw` compare); the edited file parses under
  `python3 -c 'import tomllib,…'` with exit 0.
- A `version = "3.0.0"` file makes `dev` error with a message containing `dev migrate`; an unknown
  status errors; a slug/stem mismatch errors; a task labelled `-robot` errors naming the three
  attribution labels.
- A second repository row with the same slug makes `dev alpha` error with `--repo`, and `--repo`
  resolves it.
- `dev alpha --md` equals the expected Markdown for the fixture.

Phase 3 (`new`, `migrate`):

- `hooks-placement.issue.toml` copied into `docs/issues`: `dev migrate hooks-placement --dry-run`

## Naming

Exported names are `main`, `list`, `query`, `edit`, `new`, `migrate` (and `sync` from the next
spec). A module's exported names are predeclared before its imports are parsed, so an exported
`update`, `rm`, `find`, `get` or `export` would shadow the builtin inside `util`, `todo`, `repo` or
`completion` and break their parse. `edit` and `list` are proven safe (`todo` and `hook` export them
while importing `util`). Run the ide-check after adding every export.
